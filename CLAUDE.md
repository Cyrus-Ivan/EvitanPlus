## Project status

The Laravel + React (Inertia) + NativePHP + SQLite app is **released — all 19 `ROADMAP.md` phases complete, first production release tagged `v1.0.0`** (2026-07-19, Linux AppImage + deb; see `RELEASE-NOTES.md`): the full commerce chain (Setup, DB schema, Auth, Authorization, Settings, Inventory, Ledger, CSV Import/Export, POS, Transactions, Returns/Defects, Receipt Printing, Reports incl. PDF export), the full admin/ops track (User Management, Login History, Audit Logs, Database Backup/Restore incl. external drive), the UI polish pass, the **Phase 18 final review** (429 backend tests + 10 Playwright E2E specs, invariants enforced by DB triggers + model guards, business timezone Asia/Manila — see `docs/phase-18-findings.md`), and **Phase 19 release preparation** (once-per-launch provisioning, per-install `APP_KEY`, WAL-aware backup/restore, About page, release build pipeline — see the `README.md` "Building a release" section). **Post-v1.0.0:** a fresh install runs a pre-login **setup wizard** (`/setup`, gated by `RequireInitialSetup`). As of **M5** it is a *connect-and-hydrate* flow, not an Owner-creation one: the developer imports the branch credentials JSON the provisioning console emitted, and one atomic submit connects to Postgres as the branch role, clears the version gate, copies the business baseline (catalog, all users, settings, this branch's stock) into local SQLite, seals the credential under the per-install `APP_KEY`, and writes the `instance` row whose `hydrated_at` is now the fresh-install signal. The Owner comes from provisioning; only the printer step is still collected on the device. Nothing persists unless the whole cycle succeeds. As of **M6** the device also syncs **upward**: every local-write row is enqueued in a local `sync_outbox` on create, and a **sync cycle** (probe → version gate → push, `App\Support\Sync\SyncCycle`) inserts them into Postgres idempotently, stamping `branch_id` from `instance`. Receipt serials now carry the branch code (`MNL-0000000001`) and are stored that way; the header shows an unsynced count and a "Sync now" button on every screen. **M6.5** added the other half: shared business data (catalog, staff, settings, CSV import) is written to Postgres *and* SQLite as one atomic **online write** (`App\Support\Sync\OnlineWrite`) and refused offline, so a product created at one branch reaches every other. That required widening `BranchGrants` with INSERT/UPDATE on those five tables — DELETE stays granted on nothing — plus `schema:reapply-grants` to deliver the change to already-provisioned businesses. **M7** closed the loop downward: a **pull** (`App\Support\Sync\Puller`) brings deltas of the catalog, users, settings and this branch's `stock_adjustment` ledger rows down on a per-table cursor (`sync_cursor`, bookmarked by Postgres's own watermark string, compared with `>=`), and `StockReconciler` sets local stock to `baseline + Σ(signed unsynced movements)` rather than ever overwriting it. **M8** filled the last hole in the cycle: an Owner or Admin, online, can aim a stock adjustment at *another* branch, which lands in Postgres's `inventory_update_queue` as `pending` (`InventoryQueueController`, and a target-branch select on the existing adjust dialog); that branch answers it itself in **step 2** of its own cycle (`App\Support\Sync\QueueProcessor`), **accepting** when `upstream snapshot + Σ(signed unsynced local) + quantity ≥ 0` and **rejecting** otherwise, so neither side can go negative. An accepted row is written as a ledger entry **upstream only** and rides the same cycle's pull back down, keeping one writer for `type = 'stock_adjustment'` — which is why step 2 sits between push and pull. The entry's id *is* the queue row's id, so a cycle that dies mid-resolution cannot re-decide an adjustment it already applied. An adjustment aimed at *this* branch is unchanged and still direct: the queue exists because the issuer cannot see the target's unsynced sales. `branches` and the queue are read live through a new **online read** (`App\Support\Sync\OnlineRead`) and mirrored nowhere; `/inventory/stock-updates` shows every row and its answer. Required widening `BranchGrants::INSERT` (delivered by `schema:reapply-grants`), which knowingly extends the cross-branch reach by one table — since settled as an **accepted risk**: row-level security between branches is deliberately not planned, so the enumerated grant matrix is the only boundary of its kind and must not erode (`docs/glossary.md` §9 is normative on both). A cycle is now `version gate → push → queue → pull → heartbeat`. **M9** completed the other end of that version gate, which had been readable but **unraisable**: `schema_meta` was written once by migration 000001, so a twentieth migration would have left every business declaring schema version 1 with a min-app floor of 1.0.0 forever, and a breaking change could never freeze the branches it needed to. The pair now lives in one place (`Provisioning\Support\SchemaVersion`) and `schema:migrate` **stamps** it (`SchemaStamp`) after every clean run — only when it changed, so `applied_at` still means "when this schema reached this version", and never backwards, since a schema ahead of the console running against it was migrated by a newer checkout and lowering it would un-freeze branches a breaking migration deliberately froze. The same command gained `--all` (every `biz_*` schema, not only the provisioned ones — provisioned-ness is *defined* by having the very tables a schema needing migration may lack), a `schema.migrate` audit row, and the thing four documents had promised since M1: it re-applies the branch grant matrix to every schema that **advanced** — a run where at least one pending migration actually ran — because grants are enumerated per table, so a migration that adds one leaves every branch role holding nothing on it and the till reports "Sync stuck". Console surfacing stops at the schema: `schema:migrate` says which builds a raised floor has just frozen, but *which tills* are on them needs `branch_status`, which nothing writes until M10. The version-pair discipline is **half-enforced on purpose**: `SCHEMA_VERSION` *is* the migration-file count and a test asserts it (so adding a migration fails the console suite until you bump it), and the floor may never exceed the app version `config/nativephp.php` builds — but whether a migration is *breaking*, and so whether `MIN_APP_VERSION` must rise, is not decidable by any check and stays a human call. The enforceable half exists largely to force that question at the moment it arises. **M10** added the step that gap named and the console screen that reads it: `App\Support\Sync\Heartbeat` upserts this branch's `branch_status` row as **step 4**, inside the cycle's own connection (never a connection of its own) and on **both** ways out of it — after the pull on success, and from a `catch` before the exception is re-thrown, since a branch frozen by the version gate is invisible to the console unless it says so itself. It swallows its own failures: a report about a cycle may never become that cycle's outcome. Only two of the four `connection_state` words can ever be written — `offline` and `unauthorized` are diagnosed by the connection failing to open, and a branch that cannot connect cannot report it — so the monitor's real signal is the **age of `last_seen_at`** (reached Postgres) as against `last_sync_at` (completed a cycle), which a failed beat deliberately leaves standing. The console side is `monitor` (no target = every business), read-only and unaudited like `branch:list`, on the main menu and on each business screen; it LEFT JOINs the branch roster onto the heartbeats so a branch that has never reported prints `never`, and prints the credential state of any branch that is not `active` — a credential the console disabled and a dead router produce identically silent tills. The four-word vocabulary is now the schema's rule rather than a convention (console migration `000020`), which raised `SCHEMA_VERSION` to 20 with `MIN_APP_VERSION` untouched at 1.0.0 (additive) and is the first real exercise of M9's stamp-and-re-grant machinery. **M11** finally lets one till see the whole business: `/reports` gained a **`scope`** parameter — `local` (SQLite, offline, the default and the only value an Admin may use), `all`, or a branch id — and the recompute moved out of the controller into `App\Support\Reports\SalesFigures`, which takes the **connection as an argument** so there is exactly one copy of "net sales = sales − returns − defects" whichever database answers. The consolidated scope is an **online read** (no version gate, per that class's standing reason) and is refused *inside* the controller, not by route placement, since the same route still serves the branch-local report an Admin is entitled to. Three things do not port between the two databases and all fail silently: `strftime` vs `to_char` (format inlined from a constant map, timezone **bound** because it is an Owner-editable setting); the window bounds, which must carry both their **offset** (Postgres reads a naive bound in the session's UTC — eight hours out) and their **microseconds** (`endOfDay()` is `.999999`, `timestamptz` keeps them, `toIso8601String()` truncates), while the filter stays on the raw column so the `(branch_id, created_at)` indexes still apply; and `numeric` SUMs, which arrive as exact strings rather than floats. A report row is a time bucket **or a branch** depending on one GROUP BY, so the per-branch table is the same seven aggregates and foots to the totals by construction — a branch that sold nothing prints zeros, and the roster is read *without* filtering `disabled_at` (a disabled branch cannot receive work but its past sales are still the business's). A failed read **falls back to the branch-local report and says so**; presenting one branch under an "All branches" heading is the one outcome worse than an error. Nothing here needed a schema or grant change — the first phase since M6.5 of which that is true — which also means the consolidated report reads other branches' rows on **app-layer authority alone**, the first feature to lean on §9's accepted no-RLS risk by design. Because no test device holds a sealed credential and the SQLite stand-in cannot run `to_char`, the arithmetic is provable only in `tests/Integration/ConsolidatedReportTest.php` against two really provisioned branches. Polling for the backlog was replaced by an **outbox listener** riding the shared `sync` prop — which also retired M6's post-checkout special case — leaving a single hard-coded 5-minute timer whose job is now the pull, since nothing local signals that another branch changed a price. M7 also had to make the **manual stock adjustment online-only**: it wrote a local-only ledger row the outbox deliberately excludes, so the new baseline would have silently reverted every shelf recount. Forced password change remains for admin resets. Void was dropped from Phase 10 — after-sales events are returns and defects only. Per-phase implementation notes live in the agent memory index, not here — treat this paragraph as approximate and confirm current progress against `git log` and the code.

`BRAINSTORM.md` is the full functional spec and `ROADMAP.md` is the phased build plan. `docs/returns-refunds-voids-design.md` (after-sales) and `docs/receipt-printing-design.md` (printing) are the designs of record for their areas — where `BRAINSTORM.md`/`ROADMAP.md` disagree with them, the design docs win.

## Vocabulary

`docs/glossary.md` is **normative** for this project's terminology and **outranks every other document** — including this one and the design docs — on what a word means. Read it before writing anything against a spec. It exists because a large share of the multi-branch initiative's "As built" corrections were not design changes but a word meaning one thing in the spec and another in Postgres: a grant named on a column that a check constraint made unusable, a `branch:delete` that deletes no branch, a "credential" that is really two values. Each cost implementation time to rediscover.

Two rules:
- **A word that carries weight in a spec or a phase note gets an entry**, with the code artifact that anchors it. A term with no anchor is one two people can read differently.
- **Don't coin a synonym for a defined term.** If a needed distinction has no word yet, add the entry rather than inventing a word in passing — that is precisely how `till`/`device`/`instance`, `outbox`/`queue`, and `mirrored`/`readable`/`pulled` each became three words for what readers assumed was one thing.

Naming: **Evitan POS** is the shipped single-install, offline-only product (`v1.0.0`); **Evitan Plus** is the multi-branch, cloud-connected product the `M0–M12` initiative builds. They are different products with different application ids and data directories, not old and new spellings of one name (`RELEASE-NOTES.md`). Use "Evitan Plus" for user-facing names unless told otherwise.

## What this is

Evitan Plus is an **offline-first retail Point of Sale** desktop app for a **single business installation**. No server, no cloud, no network dependency. Multi-branch and cloud sync are explicitly out of scope for the MVP but the schema should stay sync-compatible (hence UUIDs everywhere).

## Stack

- **Laravel 12** (backend) + **React 19 / TypeScript** (frontend) over **Inertia**, from the Laravel React starter kit. Pinned to Laravel 12 for NativePHP compatibility.
- **NativePHP** to package it as a native desktop executable.
- **SQLite** as the only database (`database/nativephp.sqlite`, shared by terminal artisan and the NativePHP runtime). Foreign key enforcement is on.

Standard Laravel workflow applies: `php artisan migrate` (or `migrate:fresh --seed`), `php artisan test` (Pest/PHPUnit), `npm run dev` / `npm run build`, `npm run lint`, `./vendor/bin/pint`, and NativePHP's `php artisan native:serve` / `native:build`. Dev login is `owner` / `password` (from the local demo seed, which also writes a fake `DEV` branch identity so the app is not funnelled to the wizard; packaged fresh installs have neither and run the setup wizard). Three gates, not one: `composer verify` (offline, credential-free), `composer verify:console` (the console suite + schema parity, real Supabase), `composer verify:hydrate` (provisions a throwaway business and hydrates a device from it, real Supabase). Verify script details in `composer.json` / `package.json` if in doubt.

## Non-negotiable invariants

These rules span the entire codebase and are the reason the architecture looks the way it does. Violating them is a correctness bug, not a style choice. Full detail is in `BRAINSTORM.md`.

**Immutable business history**
- Historical transactions, transaction items, and their captured prices **never change**. Selling price / item cost edits must not retroactively alter past sales — prices and costs are snapshotted onto each transaction item at time of sale.
- The inventory ledger is **append-only**. Never edit or delete a ledger row. Corrections are new compensating entries.
- Audit logs and login history are immutable and append-only.

**Never delete business records**
- Categories, Items, Variants → **archived** (flag), not deleted. Hidden from default lists, still visible via Archived filter and in all historical records.
- Users → **soft deleted**. Archived users must still appear in Sales, Login History, and Audit Logs.

**Inventory is ledger-derived**
- There is **no stock-adjustment table**. All stock movement — sales, returns, defects, manual adjustments, CSV imports — is expressed as inventory ledger entries.
- Current stock = ledger sum reconciled against a stock snapshot that is updated on every ledger insert.
- **Negative inventory is never allowed.** Enforce at write time.
- Returns restore stock (new positive ledger entry); **defects do not** restore stock.

**Identity & keys**
- Every table uses a **UUID primary key**. The transaction number is a separate human-readable value: a **continuous, gapless, zero-padded running serial** (`0000000001`, never resets — the BIR-compliant CRM/POS shape) that serves as both the internal transaction id and the customer-facing receipt number (there is no separate `receipt_number` column).
- Uniqueness: username unique; **Item name unique** (case-insensitive, spanning archived items); SKU **required**, unique, and stored uppercase; barcode unique *when provided* (blank barcode is allowed and must not block selling). **Variant names are not unique** — different items may reuse "Small"/"Large".
- Every Item must have **at least one Variant**. Stock, price, SKU, and barcode live on the Variant, not the Item. A single-product item keeps exactly one **unnamed** variant (`name` is null) — the "no variant" case; UI and reports fall back to the item name.

**Roles & permissions** (Owner > Admin > Cashier)
- Exactly **one Owner**; the Owner can never be archived or deleted.
- **Item Cost is Owner-only** to view and edit — Admins and Cashiers must never see it, including in reports and API responses. Cashiers get view-only inventory and cannot see cost.
- Enforce permissions at every layer: routes, actions, components, and buttons.

**Point of sale**
- Printing and cash-drawer opening happen after checkout but a **printing failure must never cancel or roll back a completed sale** — the sale commits, the user sees a clear error, and the receipt can be reprinted.
- Out-of-stock products stay visible but disabled.
- Discounts: amount (capped at transaction total) or percentage (capped at 100%). Split payments are out of scope.

**Reporting**
- Reports **recompute** totals from sales minus returns minus defects. Never trust a single stored total for reporting.

**Auditability**
- Every significant action (auth events, user/inventory/price changes, imports/exports, backups, restores, settings changes) writes an audit log entry.

**The Provisioning Console never ships** (Evitan Plus)
- `console/` is a separate, developer-only Laravel CLI app holding admin Postgres credentials. Its code and credentials must never appear in any AppImage/deb/build. Enforced structurally (separate app, no runtime reference from the POS app) plus `nativephp.cleanup_exclude_files` / `cleanup_env_keys`, and gated by `tests/Feature/Build/BuildExclusionTest.php`. See `MULTIBRANCH-BRAINSTORM.md` §18.

## Build order

Follow `ROADMAP.md` phases in sequence. The guiding principle is to complete each feature **end-to-end** (migration → backend → frontend → validation → permissions → audit logging → tests) before starting the next, keeping the app runnable at every phase. Do not open several major modules at once. Order: Setup → DB schema → Auth → Authorization → Settings → Inventory → Ledger → CSV Import/Export → POS → Transactions → Returns/Defects → Printing → Reports → User Management → Login History → Audit Logs → Backup/Restore → Polish → Testing → Release.
