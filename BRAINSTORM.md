# BRAINSTORM.md

# Evitan POS MVP

> **Scope.** This is the functional spec of **Evitan POS** — the single-install,
> offline-only product released as `v1.0.0`. It is **still the spec of record for the
> commerce chain** (POS, inventory, ledger, returns, discounts, reports, settings, audit,
> archiving, UUID policy): the `M0–M12` multi-branch initiative did not change those rules,
> and the code still implements what is written below.
>
> What it does **not** cover is everything that initiative added — branches, provisioning,
> Postgres, the sync cycle — specified in `MULTIBRANCH-BRAINSTORM.md`. Read the two together;
> where this document says multi-branch is out of scope, it is describing the MVP's
> boundaries, not the current product's.
>
> `docs/glossary.md` §1 is normative on the Evitan POS / Evitan Plus split, and outranks this
> document on what any term means.

## Overview

Evitan POS is an **offline-first Retail Point of Sale (POS)** application built using:

* Laravel
* NativePHP
* React
* SQLite

The objective of this MVP is to build a **fully functional local retail POS** with no server dependency. The application must be simple, reliable, and production-ready while intentionally avoiding unnecessary enterprise features.

The project should prioritize:

* Simplicity
* Reliability
* Fast checkout
* Offline operation
* Complete auditability
* Clean architecture
* Future compatibility for synchronization and multi-branch support

The application is intentionally designed for a **single business installation**. Multi-branch support and cloud synchronization are future milestones and are **not part of the MVP**. *(Both were subsequently built by the `M0–M12` initiative that turned this product into Evitan Plus — see `MULTIBRANCH-BRAINSTORM.md`. The "future compatibility" bullet above is why that was possible without rewriting the schema.)*

## Variants

Every Item must contain at least one Variant.

Fields

* UUID
* Variant Name (Nullable — a single-product item keeps exactly one **unnamed** variant, the "no variant" case; UI and reports fall back to the item name)

* Selling Price
* Item Cost (Nullable, Owner Only)
* Low Stock Threshold
* Archived Flag

Rules

* Variant names are **not** unique — different items may reuse "Small"/"Large".
* Barcode is optional.
* Blank barcode does not prevent selling.
* Search falls back to SKU or Product Name.
* Archived variants remain available for historical records.

# Inventory Stock

Inventory is computed entirely from the Inventory Ledger.

Current stock is calculated using

```
Ledger Sum
+
Stock Snapshot
```

A stock snapshot is updated after every ledger insertion.

Negative inventory is never allowed.

Rows below the configured Low Stock Threshold should be highlighted.

# Sales

Sales consist of

* Transactions
* Transaction Items

Transaction Number Format

```
0000000001
```

A **continuous, gapless, zero-padded running serial** that never resets (no date component — the timestamp lives in `created_at`). This supersedes the original `YYYYMMDD-HHMMSS-000001` daily-reset spec: a unique, consecutive, non-resetting serial is the shape a BIR-registered CRM/POS document number must take. Full BIR accreditation (ATP range/prefix, machine serial, VAT breakdown) is a deliberate future item — only the number shape is done.

The transaction number doubles as the receipt number; there is no separate receipt-number column.

---

* Transaction Number (doubles as the receipt number)

* Payment Type
* Discount

Supported Payment Types

* Cash

# Returns & Defects

> **Authoritative schema and rules live in `docs/returns-refunds-voids-design.md`** — the
> design of record. Returns/defects are **NOT** stored as additional transaction items
> (that would mutate a completed sale and break immutable business history). They live in a
> dedicated `sale_returns` / `sale_return_items` table family that *references* the original
> sale without ever changing it. The summary below is intent only; implement per the design doc.
>
> **Void was removed** — it duplicated cancelling a sale at the POS before checkout (unselect
> the item from the cart), which is already supported. Post-checkout, use returns.

## Returns

Returns are supported.

Rules

* Partial returns allowed.
* Multiple returns allowed.
* Total returned quantity must never exceed the originally sold quantity.
* Returns always use the original selling price stored in the transaction.
* Returns generate Ledger entries.
* Returns are recorded in `sale_returns` / `sale_return_items` (never added to the original transaction).
* Original sale remains unchanged.

Returned inventory goes back into stock.

## Defects

Defects represent written-off products that do not return to inventory.

Rules

* Generates a 0-movement Ledger entry (audit trail only; stock unchanged).
* Recorded in `sale_returns` / `sale_return_items`; original sale remains unchanged.
* Inventory is not restored.

Reports recompute totals by subtracting returns and defects.

# Business Rules Summary

* Offline-first.
* SQLite only.
* One logged-in user.
* UUID everywhere.
* One Owner only.
* Owner cannot be deleted.
* Username must be unique.
* Item name must be unique (case-insensitive, spanning archived items).
* SKU is required, unique, and stored uppercase.
* Barcode must be unique when provided.
* Every Item requires at least one Variant.
* Inventory never becomes negative.
* Ledger is append-only.
* Snapshot updates every ledger insert.
* Sales create Transaction and Ledger entries.
* Stock Adjustments create Ledger entries only.
* Returns restore stock.
* Defects do not restore stock.
* Historical sales never change.
* Reports recompute totals.
* Selling price changes never affect old transactions.
* Item Cost is Owner-only.
* Archived inventory is hidden by default.
* Archived inventory remains visible in historical records.
* Printing failure never cancels a sale.
* Every important action is auditable.
