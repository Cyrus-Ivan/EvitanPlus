## Project status

The Laravel + React (Inertia) + NativePHP + SQLite app is **released — all 20 `ROADMAP.md` phases (0–19) complete, first production release tagged `v1.0.0`** (2026-07-20, Linux AppImage + deb; see `RELEASE-NOTES.md`): the full commerce chain (Setup, DB schema, Auth, Authorization, Settings, Inventory, Ledger, CSV Import/Export (export since removed — M13), POS, Transactions, Returns/Defects, Receipt Printing, Reports incl. PDF export — that export since replaced by email, M14), the full admin/ops track (User Management, Login History, Audit Logs), the UI polish pass, the **Phase 18 final review** (396 backend tests + 9 E2E specs green *at that review's close*, invariants enforced by DB triggers + model guards, business timezone Asia/Manila — see `docs/phase-18-findings.md`; the suite has moved on since, and `tests/e2e/` now holds 7 specs), and **Phase 19 release preparation** (once-per-launch provisioning, per-install `APP_KEY`, About page, release build pipeline — see the `README.md` "Building a release" section). **Post-v1.0.0:** a fresh install runs a pre-login **setup wizard** (`/setup`, gated by `RequireInitialSetup`). As of **M5** it is a *connect-and-hydrate* flow, not an Owner-creation one: the developer imports the branch credentials JSON the provisioning console emitted, and one atomic submit connects to Postgres as the branch role, clears the version gate, copies the business baseline (catalog, all users, settings, this branch's stock) into local SQLite, seals the credential under the per-install `APP_KEY`, and writes the `instance` row whose `hydrated_at` is now the fresh-install signal. The Owner comes from provisioning; only the printer step is still collected on the device. Nothing persists unless the whole cycle succeeds. As of **M6** the device also syncs **upward**: every local-write row is enqueued in a local `sync_outbox` on create, and a **sync cycle** (probe → version gate → push, `App\Support\Sync\SyncCycle`) inserts them into Postgres idempotently, stamping `branch_id` from `instance`. Receipt serials now carry the branch code (`MNL-0000000001`) and are stored that way; the header shows an unsynced count and a "Sync now" button on every screen. **M6.5** added the other half: shared business data (catalog, staff, settings, CSV import) is written to Postgres *and* SQLite as one atomic **online write** (`App\Support\Sync\OnlineWrite`) and refused offline, so a product created at one branch reaches every other. That required widening `BranchGrants` with INSERT/UPDATE on those five tables — DELETE stays granted on nothing — plus `schema:reapply-grants` to deliver the change to already-provisioned businesses. **M7** closed the loop downward: a **pull** (`App\Support\Sync\Puller`) brings deltas of the catalog, users, settings and this branch's `stock_adjustment` ledger rows down on a per-table cursor (`sync_cursor`, bookmarked by Postgres's own watermark string, compared with `>=`), and `StockReconciler` sets local stock to `baseline + Σ(signed unsynced movements)` rather than ever overwriting it. **M8** filled the last hole in the cycle: an Owner or Admin, online, can aim a stock adjustment at *another* branch, which lands in Postgres's `inventory_update_queue` as `pending` (`InventoryQueueController`, and a target-branch select on the existing adjust dialog); that branch then answered it automatically in step 2 of its own cycle — *superseded by M11.7, below, which deleted that step*. `branches` and the queue are read live through a new **online read** (`App\Support\Sync\OnlineRead`) and mirrored nowhere. Required widening `BranchGrants::INSERT` (delivered by `schema:reapply-grants`), which knowingly extends the cross-branch reach by one table — since settled as an **accepted risk**: row-level security between branches is deliberately not planned, so the enumerated grant matrix is the only boundary of its kind and must not erode (`docs/glossary.md` §9 is normative on both). **M9** completed the other end of that version gate, which had been readable but **unraisable**: `schema_meta` was written once by migration 000001, so a twentieth migration would have left every business declaring schema version 1 with a min-app floor of 1.0.0 forever, and a breaking change could never freeze the branches it needed to. The pair now lives in one place (`Provisioning\Support\SchemaVersion`) and `schema:migrate` **stamps** it (`SchemaStamp`) after every clean run — only when it changed, so `applied_at` still means "when this schema reached this version", and never backwards, since a schema ahead of the console running against it was migrated by a newer checkout and lowering it would un-freeze branches a breaking migration deliberately froze. The same command gained `--all` (every `biz_*` schema, not only the provisioned ones — provisioned-ness is *defined* by having the very tables a schema needing migration may lack), a `schema.migrate` audit row, and the thing four documents had promised since M1: it re-applies the branch grant matrix to every schema that **advanced** — a run where at least one pending migration actually ran — because grants are enumerated per table, so a migration that adds one leaves every branch role holding nothing on it and the till reports "Sync stuck". Console surfacing stops at the schema: `schema:migrate` says which builds a raised floor has just frozen, but *which tills* are on them needs `branch_status`, which nothing writes until M10. The version-pair discipline is **half-enforced on purpose**: `SCHEMA_VERSION` *is* the migration-file count and a test asserts it (so adding a migration fails the console suite until you bump it), and the floor may never exceed the app version `config/nativephp.php` builds — but whether a migration is *breaking*, and so whether `MIN_APP_VERSION` must rise, is not decidable by any check and stays a human call. The enforceable half exists largely to force that question at the moment it arises. **M10** added the step that gap named and the console screen that reads it: `App\Support\Sync\Heartbeat` upserts this branch's `branch_status` row as **step 4**, inside the cycle's own connection (never a connection of its own) and on **both** ways out of it — after the pull on success, and from a `catch` before the exception is re-thrown, since a branch frozen by the version gate is invisible to the console unless it says so itself. It swallows its own failures: a report about a cycle may never become that cycle's outcome. Only two of the four `connection_state` words can ever be written — `offline` and `unauthorized` are diagnosed by the connection failing to open, and a branch that cannot connect cannot report it — so the monitor's real signal is the **age of `last_seen_at`** (reached Postgres) as against `last_sync_at` (completed a cycle), which a failed beat deliberately leaves standing. The console side is `monitor` (no target = every business), read-only and unaudited like `branch:list`, on the main menu and on each business screen; it LEFT JOINs the branch roster onto the heartbeats so a branch that has never reported prints `never`, and prints the credential state of any branch that is not `active` — a credential the console disabled and a dead router produce identically silent tills. The four-word vocabulary is now the schema's rule rather than a convention (console migration `000020`), which raised `SCHEMA_VERSION` to 20 with `MIN_APP_VERSION` untouched at 1.0.0 (additive) and is the first real exercise of M9's stamp-and-re-grant machinery. **M11** finally lets one till see the whole business: `/reports` gained a **`scope`** parameter — `local` (SQLite, offline, the default and the only value an Admin may use), `all`, or a branch id — and the recompute moved out of the controller into `App\Support\Reports\SalesFigures`, which takes the **connection as an argument** so there is exactly one copy of "net sales = sales − returns − defects" whichever database answers. The consolidated scope is an **online read** (no version gate, per that class's standing reason) and is refused *inside* the controller, not by route placement, since the same route still serves the branch-local report an Admin is entitled to. Three things do not port between the two databases and all fail silently: `strftime` vs `to_char` (format inlined from a constant map, timezone **bound** because it is an Owner-editable setting); the window bounds, which must carry both their **offset** (Postgres reads a naive bound in the session's UTC — eight hours out) and their **microseconds** (`endOfDay()` is `.999999`, `timestamptz` keeps them, `toIso8601String()` truncates), while the filter stays on the raw column so the `(branch_id, created_at)` indexes still apply; and `numeric` SUMs, which arrive as exact strings rather than floats. A report row is a time bucket **or a branch** depending on one GROUP BY, so the per-branch table is the same seven aggregates and foots to the totals by construction — a branch that sold nothing prints zeros, and the roster is read *without* filtering `disabled_at` (a disabled branch cannot receive work but its past sales are still the business's). A failed read **falls back to the branch-local report and says so**; presenting one branch under an "All branches" heading is the one outcome worse than an error. Nothing here needed a schema or grant change — the first phase since M6.5 of which that is true — which also means the consolidated report reads other branches' rows on **app-layer authority alone**, the first feature to lean on §9's accepted no-RLS risk by design. Because no test device holds a sealed credential and the SQLite stand-in cannot run `to_char`, the arithmetic is provable only in `tests/Integration/ConsolidatedReportTest.php` against two really provisioned branches. **M11.5** is three visibility gaps that earlier phases assumed rather than built, and the first slice since M6.5's numbering to sit between phases: (1) an **`identity` shared prop** (business name from the pulled settings, branch name/code from `instance`) rendered on every screen — in the sidebar footer beneath the signed-in user, and beside the sync indicator on the login screen, which has no sidebar — neither name had appeared in a single `.tsx` file, though the till has known both since M5/M7; (2) **`POST /sync` moved out of the `auth` group**, because the cycle's *pull* is what brings `users` down, so a staff member created at another branch could not log in on a device until somebody **else** logged in first — a genuine lock-out, fixed without touching the cycle at all (`SyncCycle::run()` takes no arguments and reads its identity from `instance` and the sealed credential), and still gated by `RequireInitialSetup`; and (3) a **`scope` parameter on `/login-history`** — the same `local | all | branch id` shape M11 gave reports, now the shared term **branch scope** — plus a Branch column in both views. Nothing needed a schema, grant or console change: Postgres has carried `login_history.branch_id` with a `(branch_id, occurred_at)` index since M1 and `BranchGrants` has granted SELECT on it since M2, and nothing read either for ten phases. The **local** table still has no `branch_id` and deliberately never will — every local row is this branch's by construction and the push stamps one from `instance`, so the column is filled from `instance` and is a statement about the *device*. Unlike reports the wider scopes are **Admin+** (no cost or profit is involved, and §6 names both roles) and a Cashier asking for one is **snapped back to `local` rather than refused**, since the local view is theirs by right on the same route. M11's roster query became `App\Support\Sync\BranchRoster` now that two screens share its decision to include disabled branches. Two corrections came out of it: the triggers' "mount in exactly one place" rule means one mount **at a time** (the auth layout and the app header never coexist, so the e2e trigger counts are unchanged); and M11's claim that the window bounds need their **microseconds** is **false for this schema** — `timestampTz` takes Laravel's default precision of 0, so every timestamp column is `timestamp(0) with time zone` and a `.999999` value is unrepresentable rather than merely untested. The **offset** half is real and is what `tests/Integration/ConsolidatedLoginHistoryTest.php` proves. Polling for the backlog was replaced by an **outbox listener** riding the shared `sync` prop — which also retired M6's post-checkout special case — leaving a single hard-coded 5-minute timer whose job is now the pull, since nothing local signals that another branch changed a price. M7 also had to make the **manual stock adjustment online-only**: it wrote a local-only ledger row the outbox deliberately excludes, so the new baseline would have silently reverted every shelf recount. **M11.6** removed the **Database Backup** feature outright — controller, manager, page, routes, the `access-backup` gate, the post-restore restart flow — and closed the gap that opened. Backup existed because a single offline install had one copy of its data; a branch has Postgres, and a dead device is replaced through the wizard. But hydration copied only the baseline and skipped history, so a replacement till came up with the right catalog and stock and an empty `/sales`, `/audit-logs` and `/login-history`. `Hydrator` now also copies **this branch's** `transactions`, `transaction_items`, `sale_returns`, `sale_return_items`, `inventory_ledger`, `login_history`, `audit_logs` and `import_history` — in FK order, scoped by `branch_id` (detected via `RowMapper::isBranchScoped()`, with the two line-item tables filtered through their parents), and written **`insertOrIgnore`** because seven of the eight carry `BEFORE UPDATE` immutability triggers that an `upsert` would fire on any re-hydrate. No schema, grant or console change was needed — every one of those tables was already `MIRRORED` and already had `BranchGrants::SELECT`; nothing had ever asked for it. It also fixed a latent wipe: `LaunchProvisioner` runs `inventory:reconcile` on every launch, and a pre-M11.6 hydrated device had snapshots with no ledger behind them, so the first launch after setup zeroed every variant — safe now because upstream a snapshot *is* its ledger sum (`RemoteStock::recompute()`). The shared `DirectoryPicker` moved to `App\Support\Setup\CredentialsFilePicker`, trimmed to the one method the wizard uses. Unsynced offline work on dead hardware remains unrecoverable, and nothing in the product claims otherwise any more. **M11.7** stopped stock moving because somebody typed a number: **every** stock movement — a recount at this till, a CSV import, an adjustment aimed at another branch, and both legs of the new **transfer** — now writes a `pending` row into `inventory_update_queue` (`App\Support\Inventory\AdjustmentQueue`) and stops, and a person at the *affected* branch confirms it happened before it reaches the ledger (`AdjustmentResolver`, from `/inventory/stock-updates` — a dialog on `/inventory/stock-history` for one milestone, a page in the sidebar again since). Three answers — approve, **partial approve** (`approved_quantity` + a reason), reject (a reason) — plus **Approve all** for the hundreds of rows one CSV import makes. M8 mediated only the cross-branch case because the issuer cannot see the target's unsynced sales; that was an argument about arithmetic, and arithmetic was never in doubt — a recount is a claim about a shelf somebody has to go and look at. Consequences worth knowing: `QueueProcessor` and **step 2 of the cycle are deleted** (back to `gate → push → pull → heartbeat`), `AdjustmentResolver` is the **only** writer of `type = 'stock_adjustment'` where there were three, approving writes locally *and* mirrors up (so stock moves the instant the button is pressed, not on the next pull), and the resolver **re-reads every row filtered to this branch before writing** — without that, `OnlineWrite` stamping `branch_id` from `instance` would land another branch's movement on this one's ledger. A rejection deliberately wrote **no** ledger row, on the grounds that `Puller` filters the ledger to one branch and it could never reach the branch that asked; the queue row was the record, surfaced by that page's "Sent to other branches" section — *both superseded by M11.8, below*. A **transfer** is two rows answered by two people (`parent_id` links them), and a shortfall on arrival is **written off** rather than bounced back — sender −3, receiver +2, the business one unit down, because that unit no longer exists. This is the **first raise of `MIN_APP_VERSION`** (1.0.0 → 1.1.0, schema 21): a stale build still running step 2 would auto-approve every row waiting for a human, so **migrate the schema before installing the build**. The grant widened to six columns (`approved_quantity`, `resolved_by`), `rejection_reason` became `resolution_reason`, and `inventory_ledger` gained `counterparty_branch_code` — a *code*, because Stock History must render offline and `branches` is never pulled. **M11.8** reworked that page into **Pending Stocks** and, in doing so, closed the hole the previous sentence names. A card is now a **request** — queue rows grouped by `parent_id ?? id`, one for an adjustment and two for a transfer — shown while **any** leg is still pending, with a progress stepper (Requested → Sent → Received) and the sender's answer on the receiver's card, because the receiving branch is answering for what the *sender* said actually left. Two filters, both on the URL: **branch scope** (`local | all | branch id`, ungated here — every row was already visible to every role, and what bounds *answering* one is the branch) and transfer/adjustment. The two sections and the `?resolved=1` toggle are gone, which needed somewhere for answered work to go, and the honest answer was that there wasn't one: an approved row reaches Stock History only at the branch whose stock moved, and a rejection reached nowhere at all. So **a rejection now writes a ledger row of quantity 0** — the ledger is append-only, zero sums to zero everywhere that derives stock from it, and zero-quantity rows are not new (defect audit entries have written them since Phase 11) — and **Stock History gained the same `scope` parameter** (Admin+, Cashier snapped back to `local`), modelled directly on `LoginHistoryController`. `/inventory/stock-history/{entry}/request` is a lazy JSON read of the queue row behind one ledger entry, which needs no join because `AdjustmentResolver` forces the ledger id to *be* the queue row's id; it is where "3 asked for, 2 agreed, here's why" now lives — rendered as one **block per voice** (Requested / Sent / Received), each carrying that person's name, role and branch, and *replacing* the row's Notes box rather than sitting under it, since the resolver composes that string out of exactly the same pieces. A transfer has up to three voices at three branches and the middle one was unrecorded: `secondLeg()` copies the *requester's* note onto the receiving leg and leaves the sender's answer at a branch whose ledger this device never pulls, so the resolver now joins the parent leg and writes a `Sent: 2 of the 3 asked for.` line into the offline string too. **"Ask again" is gone** (route, controller action and `can_reissue` with it): re-asking a refused transfer leg would offer stock whose shortfall the sender already wrote off, and for an adjustment it duplicated the dialog that issues one. Schema 22 adds `issued_by_branch_id` — additive, `MIN_APP_VERSION` stays 1.1.0, no grant change (INSERT/SELECT are table-level) — because the issuer's branch genuinely cannot be derived: `IssueTransferRequest` takes both branch ids as free choices, so an Owner at head office can arrange a move between two branches that are neither of them theirs. `AdjustmentResolver::approveAll()` and `POST .../resolve-all` are deleted: the page filters, so "Approve all" can only honestly mean the ids on screen, and it posts them as an ordinary batch to `resolve` (which re-reads them authoritatively anyway). **M12** gave the last two operational screens the same **branch scope**, and closed four gaps in the device-rebuild path. `/sales` takes `local | all | branch id` (Admin+, Cashier snapped back — a sales *list* carries no cost or profit, so it is not Owner-only like reports), and a remote row opens a **read-only** detail: no reprint, no return, because neither the receipt nor the stock is this branch's to act on. `{transaction}` is no longer model-bound, since under a wider scope it names a row that is not on this device; `sales.print` and `sales.returns.store` keep their binding so a remote id 404s there. Three traps, all silent: the remote search must be **`ilike`** (SQLite's LIKE is case-insensitive for ASCII and Postgres's is not, so `mnl` matches locally and nothing upstream — and `LikeQuery`'s macros are Eloquent-only anyway, so only `escape()` is shared); `withCount` does not exist on a query builder, so the line count is a second `whereIn` inside the same read rather than a join `paginate()`'s own `count(*)` would drag through twice; and ordering needs an **`id` tiebreak** at `timestamptz` precision 0. Plus the one that is not a dialect difference: `cost` is guarded by the SELECT column list *alone*, because `HidesCostFromNonOwners` is a model hook that never runs on query-builder rows. `/inventory` takes the same parameter — **minus `all`**, see below — but changes **stock and nothing else**: the item and variant list is read locally in every scope (the catalog is mirrored business-wide, so the local rows *are* the upstream rows) and the online read is one `whereIn` over `stock_snapshots` for the ids already on the page, which makes the fallback "attach nothing" and leaves no half-consolidated state to design a screen for. The scoped figure lands on **`scoped_stock`**, never `current_stock`: that is a get-only cached accessor over the local snapshot, so a write to it is discarded and the page would render this device's numbers under another branch's heading with no error. A variant the scoped branch holds no row for reads **zero** (upstream a snapshot is written the first time stock moves, so no row means none has), and what is on screen is that branch's **baseline** — its unsynced sales are not deducted, so it reads high, and the page says so. Inventory is also the one screen that offers **`local` or a branch id and never `all`** (M12 shipped it and it was since removed): everywhere else a wider scope adds rows to a *list*, but here it adds them to a *number*, and a business-wide total per variant says nothing on its own — twenty units is twenty spread evenly or twenty at one branch and none at the other four — so it needed a per-branch breakdown printed under every figure to be readable at all, and that much meaning in one table cell was the thing to remove. `normalizeScope()` snaps `?scope=all` back to `local` so it cannot return by URL, the shared `BranchScopeSelect` gained `allowAll` (default true) for the one call site that passes false, and the other five screens are untouched. Neither needed a schema, grant or console change; both lean on §9's accepted no-RLS risk, and both are provable only against real Postgres (`tests/Integration/ConsolidatedSalesTest.php`, `ConsolidatedStockTest.php`). The rebuild work: `Hydrator` now upserts on the row's **real identity** (`CONFLICT_TARGET`), because `stock_snapshots` is the one mirrored table whose uuid the two databases mint independently — so on any device that has traded, a re-hydrate keyed on `id` hit the `UNIQUE` index over `variant_id` and 500'd past the wizard's own error handling; **failed** CSV imports now reach Postgres too (a separate best-effort one-row write, since every failure path records outside the import's online write where `OnlineWrite::mirror()` has nothing to attach to); the supported device rebuild — delete the local SQLite file and relaunch — is written down at last, along with the two things it does not restore (printer configuration, unpushed outbox); and four docblocks that had claimed since M11.6 that hydration skips history were corrected. **M13** split the two jobs `/inventory` had been doing into two screens, and gave stock a way to move many products at once. The **catalog** is now `/items` (`ItemController`, page `items/index`), with Categories under it at `/items/categories`; it lost the branch `scope`, the stock and low-stock columns, and the three per-variant actions, because nothing on it is per-branch. **Stock** keeps `/inventory` under a new `InventoryController` that is the old stock half lifted whole — `normalizeScope`, the consolidated read, `scoped_stock`, `allowAll={false}` — over a **variant-first** query: one row per variant, flat, no expansion, since stock lives on the variant and a row that is an item has to hide every figure behind a chevron. That query joins `items`, which is why `Variant::scopeActive()` had to qualify its column (`variants.archived_at`) — `items` carries one too, and the unqualified version is an ambiguous-column error at runtime rather than at boot. The **CSV import** lost `stock` and `mode` outright (a spreadsheet cannot assert what is on a shelf; since schema 21 the column was only *asking* anyway), lost its page and its **export**, and became a modal on Items with a two-post flow: `items.import.preview` parses and validates and stops, so the modal can name every existing product the file would change, and `items.import.store` refuses to apply one unless `confirm_updates` says somebody looked — enforced inside `CsvInventoryImporter`, not in the modal, so a hand-built request is refused the same way. The file is **re-uploaded** on confirm rather than parked server-side: the second parse is authoritative, the apply stays all-or-nothing, and there is no temp-file lifecycle. `import_history.mode` was repurposed to the values the Postgres migration always documented — `create | update | upsert`, plus `unknown` for a file that never parsed far enough to tell. The consequence to know: **there was no bulk path for opening stock any more** — *superseded by M13.5, below, which built a narrow one.* A **stock batch** is the new one — many movements asked for as one act, sharing a nullable `batch_id` on *both* `inventory_update_queue` and `inventory_ledger` (schema 23, additive, `MIN_APP_VERSION` stays 1.1.0, **no grant change** because INSERT/SELECT are table-level and nothing ever UPDATEs the column). `StockBatchController` writes one queue row per line under one note; a transfer batch writes only the **sending** legs and `AdjustmentResolver::secondLeg()` carries the batch onto each receiving leg as the sender confirms, so both branches see one card. Pending Stocks' grouping key widened to **`batch_id ?? parent_id ?? id`**, which made a card span many products — so `item`/`variant` moved from the request onto the **leg**, and each leg gained `line` (the pairing key) and `requested`. Answering needs no new path: "Approve all" posts the card's ids to the same `resolve` route, which re-reads each of them filtered to this branch. `set` ("readjust to this number") is offered in a batch **only for this branch**, matching `IssueStockAdjustmentRequest` since M8: another branch's figure is a baseline missing its unsynced sales, so a delta derived from it is wrong by exactly what the network has not caught up with, and wrong silently. `low_stock_threshold` stayed on the item form — it looks like a stock figure and is a property of the product, the same at every branch. `RemoteStock` gained a static `read()` so the Inventory page and the batch dialog's picker share one copy of the snapshot query. **M13.5** closed the hole M13's "no bulk path for opening stock" names. A device off the wizard has every variant at **zero** — for a new business because `business:provision` seeds no catalog, for a new branch because a branch that has never traded has no `stock_snapshots` rows to hydrate — so six hundred SKUs meant six hundred lines through a dialog capped at a hundred. `App\Support\Inventory\OpeningStockImporter` takes a two-column file (`sku, quantity`, everything else ignored) from a modal on `/inventory` and writes `inventory_ledger` **directly** through `StockLedger`, inside one `OnlineWrite`, with `RemoteStock::recompute()` behind the mirror — making it the **second** writer of `type = 'stock_adjustment'`, the first deliberate one since schema 21 made `AdjustmentResolver` the only one. What bounds the carve-out is the **opening window** (`App\Support\Inventory\OpeningWindow::isOpen()`: no `type = 'sale'` row exists for this branch, so a return or a defect closes it too), enforced on the prop, in `OpeningStockImportRequest::authorize()` as a **403** rather than a field error, and again in the importer. The queue exists so a second voice can check a claim against a shelf with a past; a branch that has never sold anything has no past to contradict, the uploader is the person standing at the branch, and confirming a file you typed a moment ago is ceremony without a second voice — **do not add a third writer** (`docs/glossary.md` §4 is normative on the count and the reason). The window is **derived, never stored**, so it cannot drift and a *rebuilt* device at an established branch is correctly shut, having hydrated that branch's sales in M11.6. A quantity is the **resulting on-hand** applied as `quantity − current stock` (the batch dialog's `set`, legal here because the figure underneath is this device's own reconciled one), which makes the file re-uploadable — run it twice and every delta is zero, so a typo is fixed by fixing the cell; and a line that moves nothing writes **nothing**, including a zero on a variant at zero, which is M7's rule and the only thing keeping `stock_snapshots_non_negative` from freezing the branch forever. It cannot create products: an unknown SKU fails the whole file, which is what makes the new-branch case "the stocks of the current catalog" rather than a second door into it — hence **two files**, since folding stock back onto the item CSV would put a column there whose meaning changed over the life of the install. **No migration, grant, console or version-pair change**: `reference_type = 'csv_import'` is an unconstrained string that stayed a live movement kind through M13 with nothing writing it, `inventory_ledger` has had INSERT since M2 and `stock_snapshots` INSERT/UPDATE since M6 — so these rows render on builds back to `v1.0.0`. Two stale claims in `docs/glossary.md` §8 were corrected on the way through: `import_history` **does** sync upward and **does** have INSERT, both false there since M6.5 itself. **M14** took away the **last export in the product**: `GET reports/export` and its `Pdf::download()` are deleted with **no fallback**, and the report leaves the device as an emailed PDF or not at all — a document that lands in the Downloads folder of a shop counter has not left the building, which was the only thing anybody wanted from it. `POST reports/email` stays in the **same `role:admin` group** as the screen, because the consolidated scope is refused *inside* the controller by `normalizeScope()` exactly as it always was; a dialog on `/reports` pre-ticks the configured recipients and lets the sender untick, remove or add one **for that send only**, and `email()` reads the list from the request and never writes back. Three thin lifts out of the controller (`ReportPeriods`, `SalesReportBuilder`, `SalesReportPdf` — the last returning **bytes**, since neither a Mailable nor a console command has a response to hang a file on) let the screen, the manual send and the scheduled one produce one document; the extraction was gated on the reports tests passing **unchanged**. Every setting is **device-local** — new `report_email_*` rows in the local `settings` table deliberately *not* added to `BusinessSettings::KEYS`, which is what makes them invisible to `Puller::scope()` and `Hydrator::copySettings()`, so **no migration, no `SCHEMA_VERSION` bump, no `BranchGrants` change, no console parity edit** and nothing to mirror. That is a decision, not where the code landed: a mirrored SMTP password would sit in Postgres readable by every branch role, and it is sealed under the **per-install `APP_KEY`**, which does not travel between installs anyway. The trap worth knowing is that `AuditLog` **is** pushed upward, so the settings diff is taken over `forAudit()` — password replaced by a `(set)`/`(unset)` sentinel — and never over `all()`; there is a regression test for exactly that. Sending is **synchronous** (no queue worker exists, so nothing may be `ShouldQueue`) with an explicit 15s transport timeout and a `Mail::purge()` in a `finally`, because `MailManager` caches resolved mailers and the NativePHP PHP process is long-lived. `bootstrap/app.php` gained the app's **first `withSchedule()`**: NativePHP already ticks `artisan schedule:run` every minute *while the window is open*, so `reports:send-scheduled` runs every fifteen minutes and decides for itself whether a period is due — comparing a marker of the form `weekly:2026-08-03`, which carries the period **kind** as well as the date because a weekly window's start can equal a daily one's. Because the window is always the last *complete* period relative to now, a device off for three weeks sends **one** report, not three: a marker holds a position, not a backlog. The scheduled send is always **branch-local** (no actor to authorize a wider scope, no screen to fall back on) and omits cost unless the Owner ticks `report_email_include_cost` — the one deliberate carve-out against "Item Cost is Owner-only to view", made by the only person entitled to make it. **M14.5** replaced that single sending period with **four independent schedules** (`App\Support\Email\ReportSchedule`, one per kind), each togglable and each with a **send time**: daily also carries a Mon–Sun picker (all seven *is* "every day" — one block, not two, since an "every day" schedule beside a "selected days" one would collide on the days they share), while weekly fires on a Monday, monthly on the **first Monday of the month** and yearly on the **first Monday of the year**, each covering the period that finished before it. The whole of it is two methods: `lastDueAt()` ("when should this most recently have fired?") and `windowFor()` (which delegates to `ReportPeriods::resolveWindow()`, so there is still one copy of what a week is); `lastCompleteAnchor()` was the old answer to both at once and is deleted. `lastDueAt()` looks **backward, never forward**, which is what keeps M14's two properties intact through the addition of a time of day — a device shut at 08:00 sends *late* on the next launch rather than skipping, and one off for three weeks still sends *one* weekly report. Send times are a **closed quarter-hour list** because the tick stayed at fifteen minutes and `08:07` would fire at `08:15` with nothing on screen to say so; the tick could not be made finer *and* read the chosen times, since `bootstrap/app.php`'s closure runs on every artisan invocation (`migrate` on a bare device included) and so may not touch the database. The marker became **one key per kind** holding a bare `Y-m-d` — M14 needed the `daily:` prefix inside one shared value because a weekly window's start can equal a daily one's, and a key that names the kind makes the collision unrepresentable instead — while the backoff clock stays **shared**, so a walk that fails once stops and every kind after it keeps its unwritten marker for the retry. A local **data migration** carries an installed device forward (old period → matching toggle, old marker → matching per-kind key). The same phase let the `/reports` email dialog **pick its own period and date** instead of sending whatever the page happened to show, which needed no backend change at all: `EmailReportRequest` had validated both since M14 and `email()` had always derived its window from them. **Scope is deliberately not overridable there** — `normalizeScope()` is the sole authority on which branches a viewer may read. Still device-local throughout, so **no `SCHEMA_VERSION` bump, no `BranchGrants` change, no console parity edit, nothing mirrored**. Forced password change remains for admin resets. Void was dropped from Phase 10 — after-sales events are returns and defects only. Per-phase implementation notes live in the agent memory index, not here — treat this paragraph as approximate and confirm current progress against `git log` and the code.

## Vocabulary

`docs/glossary.md` is **normative** for this project's terminology and **outranks every other document** — including this one and the design docs — on what a word means. Read it before writing anything against a spec. It exists because a large share of the multi-branch initiative's "As built" corrections were not design changes but a word meaning one thing in the spec and another in Postgres: a grant named on a column that a check constraint made unusable, a `branch:delete` that deletes no branch, a "credential" that is really two values. Each cost implementation time to rediscover.

Two rules:
- **A word that carries weight in a spec or a phase note gets an entry**, with the code artifact that anchors it. A term with no anchor is one two people can read differently.
- **Don't coin a synonym for a defined term.** If a needed distinction has no word yet, add the entry rather than inventing a word in passing — that is precisely how `till`/`device`/`instance`, `outbox`/`queue`, and `mirrored`/`readable`/`pulled` each became three words for what readers assumed was one thing.

Naming: **Evitan POS** is the shipped single-install, offline-only product (`v1.0.0`); **Evitan Plus** is the multi-branch, cloud-connected product the `M0–M13.5` initiative builds. They are different products with different application ids and data directories, not old and new spellings of one name (`RELEASE-NOTES.md`). Use "Evitan Plus" for user-facing names unless told otherwise.

## What this is

Evitan Plus is an **offline-first, multi-branch retail Point of Sale** desktop app. Many branches of one business share a single authoritative Postgres schema on Supabase, and **every branch still sells offline**: the till reads and writes local SQLite, and a sync cycle reconciles it with the business database when the network is there. A branch that loses its connection keeps selling and catches up later; only the handful of *shared* writes (catalog, staff, settings) require being online. UUID primary keys everywhere are what make that reconciliation possible.

This is the product Evitan POS (`v1.0.0`) was evolved into — see the naming note above, and `docs/glossary.md` §1, which is normative on the split.

## Stack

- **Laravel 12** (backend) + **React 19 / TypeScript** (frontend) over **Inertia**, from the Laravel React starter kit. Pinned to Laravel 12 for NativePHP compatibility.
- **NativePHP** to package it as a native desktop executable.
- **SQLite** as the device database (`database/nativephp.sqlite`, shared by terminal artisan and the NativePHP runtime). Foreign key enforcement is on. Every screen reads it, so the app works offline.
- **Postgres on Supabase** as the business database — one schema per business (`biz_<id>`), reached over the `pgsql` connection (`config/database.php`) through `App\Support\Sync\*` using the sealed branch credential. Never the default connection; nothing reads it on the render path except the explicit online reads.

Standard Laravel workflow applies: `php artisan migrate` (or `migrate:fresh --seed`), `php artisan test` (Pest/PHPUnit), `npm run dev` / `npm run build`, `npm run lint`, `./vendor/bin/pint`, and NativePHP's `php artisan native:serve` / `native:build`. Dev login is `owner` / `password` (from the local demo seed, which also writes a fake `DEV` branch identity so the app is not funnelled to the wizard; packaged fresh installs have neither and run the setup wizard). Three gates, not one: `composer verify` (offline, credential-free), `composer verify:console` (the console suite + schema parity, real Supabase), `composer verify:hydrate` (provisions a throwaway business and hydrates a device from it, real Supabase). Verify script details in `composer.json` / `package.json` if in doubt.

## Non-negotiable invariants

These rules span the entire codebase and are the reason the architecture looks the way it does. Violating them is a correctness bug, not a style choice. Full detail is in `BRAINSTORM.md`.

**Immutable business history**
- Historical transactions, transaction items, and their captured prices **never change**. Selling price / item cost edits must not retroactively alter past sales — prices and costs are snapshotted onto each transaction item at time of sale.
- The inventory ledger is **append-only**. Never edit or delete a ledger row. Corrections are new compensating entries.
- Audit logs and login history are immutable and append-only.

**Never delete business records**
- Categories, Items, Variants → **archived** (flag), not deleted. Hidden from default lists, still visible via Archived filter and in all historical records.
- Users → **soft deleted**. Archived users must still appear in Sales, Login History, and Audit Logs.

**Inventory is ledger-derived**
- There is **no stock-adjustment table**. All stock movement — sales, returns, defects, manual adjustments, CSV imports — is expressed as inventory ledger entries.
- Current stock = ledger sum reconciled against a stock snapshot that is updated on every ledger insert.
- **Negative inventory is never allowed.** Enforce at write time.
- Returns restore stock (new positive ledger entry); **defects do not** restore stock.

**Identity & keys**
- Every table uses a **UUID primary key**. The transaction number is a separate human-readable value: the **branch code, then a continuous, gapless, zero-padded running serial** (`MNL-0000000001`, never resets — the BIR-compliant CRM/POS shape), stored in that form and serving as both the internal transaction id and the customer-facing receipt number (there is no separate `receipt_number` column). The prefix is what keeps branches minting serials independently from colliding; note that `(int) "MNL-0000000009"` is `0`, so nothing may derive the next serial by casting.
- Uniqueness: username unique; **Item name unique** (case-insensitive, spanning archived items); SKU **required**, unique, and stored uppercase; barcode unique *when provided* (blank barcode is allowed and must not block selling). **Variant names are not unique** — different items may reuse "Small"/"Large".
- Every Item must have **at least one Variant**. Stock, price, SKU, and barcode live on the Variant, not the Item. A single-product item keeps exactly one **unnamed** variant (`name` is null) — the "no variant" case; UI and reports fall back to the item name.

**Roles & permissions** (Owner > Admin > Cashier)
- Exactly **one Owner**; the Owner can never be archived or deleted.
- **Item Cost is Owner-only** to view and edit — Admins and Cashiers must never see it, including in reports and API responses. Cashiers get view-only inventory and cannot see cost.
- Enforce permissions at every layer: routes, actions, components, and buttons.

**Point of sale**
- Printing and cash-drawer opening happen after checkout but a **printing failure must never cancel or roll back a completed sale** — the sale commits, the user sees a clear error, and the receipt can be reprinted.
- Out-of-stock products stay visible but disabled.
- Discounts: amount (capped at transaction total) or percentage (capped at 100%). Split payments are out of scope.

**Reporting**
- Reports **recompute** totals from sales minus returns minus defects. Never trust a single stored total for reporting.

**Auditability**
- Every significant action (auth events, user/inventory/price changes, imports/exports, settings changes) writes an audit log entry.

**The Provisioning Console never ships** (Evitan Plus)
- `console/` is a separate, developer-only Laravel CLI app holding admin Postgres credentials. Its code and credentials must never appear in any AppImage/deb/build. Enforced structurally (separate app, no runtime reference from the POS app) plus `nativephp.cleanup_exclude_files` / `cleanup_env_keys`, and gated by `tests/Feature/Build/BuildExclusionTest.php`. See `MULTIBRANCH-BRAINSTORM.md` §18.

## Build order

Follow `ROADMAP.md` phases in sequence. The guiding principle is to complete each feature **end-to-end** (migration → backend → frontend → validation → permissions → audit logging → tests) before starting the next, keeping the app runnable at every phase. Do not open several major modules at once. Order: Setup → DB schema → Auth → Authorization → Settings → Inventory → Ledger → CSV Import → POS → Transactions → Returns/Defects → Printing → Reports → User Management → Login History → Audit Logs → Polish → Testing → Release.
